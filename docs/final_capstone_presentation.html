Why this problem matters

“Which card should I use?” is not just a multiplier lookup.

  • Rewards depend on merchant category and MCC edge cases.
  • Foreign fees can erase an otherwise strong reward.
  • Benefit terms are detailed, conditional, and change over time.
  • One confident but wrong answer can mislead a financial choice.

Intended user

A rewards-aware consumer who wants a quick, auditable comparison of cards in a wallet.

System goal

Recommend and explain a card using synthetic wallet data, deterministic calculations, and retrieved evidence.

An agent-based approach fits because the task coordinates merchant, wallet, and policy lookups with calculations; no single model response should be trusted to supply all of those facts.

Scope: recommendation, not transaction authorization2 / 8

System architecture · reasoning and memory

Evaluate every viable card branch before ranking.

1 · Yield

Category multiplier × point value × amount.

2 · Benefits

Card-filtered issuer passages support—not invent—illustrative perks.

3 · Fees

Subtract international fee; prune a branch when fee meets or exceeds yield.

Example from a deterministic test: $100 at Trader Joe’s → Amex Gold earns 680¢ base rewards (4× × 1.7¢). Perk estimates are synthetic assumptions, not cash guarantees.

RAG uses public issuer guides, local ChromaDB, MiniLM embeddings, card metadata, and MMR; source URLs and PDF page citations accompany retrieved text.

Tree of Thought is a structured evaluation tree, not free-form model scoring4 / 8

Key design decisions

Each refinement adds control where the task is uncertain.

  • Problem framing: identified MCC ambiguity, changing terms, and arithmetic as reasons not to rely on prompting alone.
  • Tools and memory: added merchant/wallet data tools and issuer-document retrieval.
  • Reasoning and coordination: added breadth-first ToT branches and LangGraph roles with typed handoffs.
  • Guardrails: validate 0 < amount ≤ $50,000; require review above $2,500 or when merchant/category context is uncertain.
  • Human control: users can confirm or correct context; stale evidence is withheld, failures are audited, and models cannot change scores or authorize purchases.
Autonomy is limited to grounded, lower-risk recommendations5 / 8

Closing reflection

Useful autonomy depends on visible boundaries.

What worked

Combining deterministic tools, retrieved evidence, structured reasoning, bounded model support, and selective review creates an auditable recommendation without granting payment authority.

What I learned

Good agent design is not just capability; it is deciding what the model cannot decide and making uncertainty actionable.

What I would improve next

Build a labeled merchant benchmark, measure calibration and reviewer burden, add item-level context, and profile latency and source freshness. Wallet and point values remain synthetic; perk estimates are illustrative, and no user study or real-world accuracy evaluation has been completed.

Any move toward real accounts or payment execution would need separate security, privacy, authorization, and compliance review.
