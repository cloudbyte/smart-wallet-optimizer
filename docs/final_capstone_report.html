Smart Wallet Rewards Optimizer

Final Capstone Report · Carnegie Mellon University Executive Education: Agentic AI · Personal Assistant Track

1. Project title

Smart Wallet Rewards Optimizer: A Grounded, Risk-Aware Payment Card Recommendation Agent.

2. Problem and user

Consumers with multiple rewards cards face scattered multipliers, merchant-category-code (MCC) exceptions, foreign transaction fees, and detailed benefit terms. A card with the highest headline multiplier may not produce the highest net value after fees, and a benefit should not be assumed merely because a model remembers it. The intended user is an everyday, rewards-aware cardholder who wants a concise, auditable comparison before paying.

3. System goal and scope

Given a merchant, amount, and international-purchase flag, the system identifies the catalog category, loads a synthetic wallet, calculates rewards, retrieves relevant card-specific evidence, compares cards, and returns a recommendation with alternatives and an audit trail. It is decision support only: no live accounts, real customer profiles, balances, payment execution, or personalized financial advice. Wallet values and perk estimates are illustrative; users must verify current issuer terms.

Success means producing a valid, explainable comparison whose calculations follow the configured wallet data, whose benefit claims cite retrieved card-specific evidence, and whose uncertain or higher-impact cases are routed for confirmation. Passing tests demonstrates behavior on specified cases, not real-world accuracy.

4. Final system architecture

A Pydantic v2 request model validates transaction inputs. A LangGraph state graph then coordinates parallel location, merchant-catalog, and wallet lookups, followed by three specialist stages:

  • Context and Rewards: resolves canonical merchant/MCC/category and calculates candidate-card yields from synthetic JSON data.
  • Benefits and Risk: retrieves card-filtered issuer passages from a local ChromaDB index when the purchase is not a low-value, local, non-high-risk case. The pipeline parses public PDF/HTML guides, records source metadata, and uses MiniLM embeddings with maximal marginal relevance (MMR).
  • Decision Orchestrator: evaluates card branches breadth-first using deterministic reward, supported illustrative perk, and fee values. It prunes frozen/expired cards and branches whose international fee meets or exceeds reward yield, applies approval rules, and assembles a structured result.

Local Qwen3 can map an uncertain merchant to a catalog candidate, critique the reasoning tree, and explain results. It cannot invent MCC data, change scores, or override constraints. Critiques must cite retrieved evidence; unsupported summaries are replaced by factual fallbacks. Streamlit and CLI share the workflow.

5. Design evolution across the program

The project evolved from a problem and tool-scoping proposal into an integrated, testable system. Early design work identified why a standalone language model was not sufficient: it lacks wallet state, can confuse merchant categories, and is unreliable at financial arithmetic and policy interpretation. Tool and memory design then added a synthetic merchant catalog, wallet access, and retrieval over public issuer guides. The ToT checkpoint made the comparison explicit: each active card is a branch evaluated for reward yield, supported benefits, and fee impact, rather than committing to the highest multiplier immediately.

Multi-agent design separated context/rewards, benefits/risk, and decision orchestration through LangGraph state. Safety work added input bounds, grounded-output checks, escalation, failure fallbacks, and a review form. The final architecture keeps computation deterministic and model contributions constrained.

6. Implementation overview

The codebase uses Python, Pydantic v2, LangGraph, Streamlit, ChromaDB, Requests, PyPDF, and Transformers. Qwen3-0.6B is the local CPU default; the Colab notebook selects Qwen3-4B for GPU execution. Sentence Transformers' all-MiniLM-L6-v2 provides embeddings. Synthetic merchant and wallet profiles live in JSON. Public issuer URLs are listed in a source manifest; downloaded terms and vector indexes are cached locally and are not committed. The README documents local and Colab setup, CLI/web usage, data, and recommendation flow.

7. Evaluation and results

The automated suite tests input validation, catalog resolution and aliases, wallet constraints, arithmetic, ToT ordering and pruning, international fees, benefit evidence and citations, approval routing, output grounding, retrieval behavior, model fallbacks, and web rendering/review. On November 19, 2026, the full suite collected and passed 72 of 72 tests in the project virtual environment. For example, a deterministic synthetic Trader Joe’s grocery case checks that the American Express Gold Card earns 680 cents in base rewards on a $100 purchase using the configured 4× multiplier and 1.7-cent point valuation. Separate tests check fee conversion, evidence-dependent perk estimates, and required confirmation for uncertain cases.

These results verify specified software behavior, not real-world accuracy. No user study, holdout benchmark, calibration study, or production latency analysis has been run. Although the audit records end-to-end latency, no representative distribution exists. Next evaluation should use labeled merchants, an independent calculation oracle, injected service failures, reviewer agreement and false-escalation measures, and p50/p95 latency. Targets must remain distinct from observed results.

8. Safety and reliability considerations

Requests require a non-empty merchant and a finite amount above zero and no greater than $50,000. Unknown merchants use a conservative miscellaneous category and require confirmation. AI-matched, category-ambiguous, low-confidence, conflicting-category, high-value (over $2,500), no-eligible-card, and benefit-retrieval-failure cases are flagged for user review. Model explanations and critiques cannot change structured financial results; optional model failures are logged and explanations fall back to verified summaries. If an expired issuer document cannot be refreshed, it is withheld rather than used as current evidence. The Streamlit review form lets the user confirm context or correct merchant/category and re-evaluate; it records review information in the response audit but does not persist corrections or change system rules automatically.

Audit entries capture tool outcomes, citations, branch scores, pruning/escalation reasons, failures, review corrections, and latency. Tests use synthetic data; the system has no payment authority. These safeguards cannot prove public documents are complete or current, and user confirmation is not issuer verification.

9. Limitations and next steps

Wallet profiles and point values are mock data; benefit values are illustrative, not actuarial. Item-level exclusions, purchase details, rotating categories, balances, and welcome-bonus progress are not fully represented. Merchant categories may differ by department or processor. Source availability and parsing affect reliability; a small local model may make weak matches. Human review is an interactive confirmation, not a staffed queue, and corrections do not drive continuous learning.

Next steps are to replace illustrative perk values with transparent, user-configurable assumptions; add item and receipt context; improve source freshness and coverage tests; collect a blinded benchmark and latency profile; measure calibration and reviewer burden; and add durable, privacy-conscious review telemetry. Any expansion toward account connections or payment execution would require a separate security, privacy, authorization, and compliance review.
